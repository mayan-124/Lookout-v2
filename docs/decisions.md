# Decisions

Deviations from, and interpretations of, the brief.

## Phase 5 B (semantic search)

Design and the folder the user fills are in `docs/semantic.md`; the index API in `docs/plugins.md`.

- **Choices (approved from the feasibility report).** `ort` 2.0.0-rc.15 pinned exactly, `load-dynamic`, only in the helper; bge-small-en-v1.5 int8; flat int8 vectors scanned brute force; helper on demand, 60 s idle stop, same host, gate and Job Object. No download code. SHA-256 pins for model, tokenizer and runtime. New dependencies: `ort` (ONNX Runtime binding; the runtime itself is not bundled), `unicode-normalization` (accent stripping in the tokenizer), `sha2` in the helper (already used by the core), `windows-sys` as a dev-dependency of the helper (private working set in the evaluation example only). No `tokenizers`, `usearch` or `sqlite-vec`.
- **The earlier prototype used mean pooling; the model card says CLS pooling.** The helper uses CLS and the query instruction prefix.
- **The content index does not store text** (only a preview), so the semantic indexer re-reads each file through the same extractor, OCR and masking. A screenshot is therefore OCR'd twice (once for full-text, once for vectors); this happens once per file and change, under the duty cycle. The indexer waits for the content worker to be idle so both together stay within one 10% duty.
- **Files without text** are sent with empty text so the helper records them and `index_needs` stops asking.
- **Similarity threshold.** Swept on the 30 tune queries only, together with 4 off-topic queries: below 0.60 every off-topic query returned results. Chosen rule: the highest top-5 among thresholds with no off-topic results, which gives 0.60 (user-editable). It costs recall: embeddings alone (no threshold) put the right file first for 49 of 50 queries, the threshold keeps 39 (see the evaluation below).
- **Off-topic queries at 2,060 files (re-check).** With 14 off-topic queries, fixed 0.60 still returns results for 10 (top-1 28, top-5 33 of 50); 0.65 leaves 5 (25, 28); 0.70 leaves 1 (17, 18). A relative rule (floor plus a margin of 0.03 to 0.10 below the best hit) gave exactly the 0.60 numbers: it never removes the best hit, so it cannot clear an off-topic query.
- No rule removes off-topic results without losing hits, so 0.60 stays the default; users who prefer fewer false results can raise `min_similarity` in the panel (0.65 is the first step).
- **"Delete my meaning index"** removes the vectors and turns the plugin off; otherwise the indexer would rebuild it at once.

### Evaluation (generated fixtures only: 48 text notes and 12 rendered screenshots read back through Windows OCR; 50 queries written before any tuning, 30 tune and 20 holdout)

| | top-1 | top-5 |
|---|---|---|
| keyword only (existing full-text and name search), all 50 | 0 | 0 |
| keyword + semantic at 0.60, tune 30 | 22 | 23 |
| keyword + semantic at 0.60, **holdout 20** | 17 | 17 |
| keyword + semantic at 0.60, all 50 | 39 | 40 |

Keyword-only scores 0 because the existing content search needs every query word to occur in the file and the queries were written to use other words; the 3 queries that deliberately share one word still fail since their other words do not match. This is a result of how the queries were built, not a general measure of keyword search. At 0.50 (not chosen; off-topic queries then return results) the holdout was 18/20 top-1 and 19/20 top-5. int8 against fp32 of the same model: mean cosine between their vectors 0.9966 (min 0.9937); embeddings alone, 60 texts: int8 top-1 49 / top-5 50, fp32 top-1 48 / top-5 50. Windows Search baseline: **skipped**; the temporary fixture folder is not in the Windows Search index and adding it means changing its indexed locations, which this task forbids.

Memory and latency (release build, this machine, 60-file index, `eval run`): helper private working set 62 MB while indexing and 62 MB warm and idle (cap 1 GiB; grows by about 0.4 MB per 1,000 files); the helper process was gone 61 s after the last call; the evaluation process standing in for the daemon measured 5.0 MB before and 5.4 MB after indexing finished (the vectors live in the helper; the difference is noise of that size); first query end to end 409 ms cold (helper not running, files in the OS cache; includes the 150 ms pause) against a median of 161 ms warm.

Not verified: embeddings against the reference `sentence-transformers` implementation (not available here); only the tokenizer is checked against a reference, and similar sentences score 0.80 against 0.32 for unrelated ones. Scale beyond 60 files was not measured; the brute-force scan was measured at 100,000 vectors in the feasibility report.

### Phase 5 follow-up: 2,060 files, fair baseline, real memory, scale

`eval run <assets> 2000` adds 2,000 generated distractor notes (40 topic pools, fixed seed; many are on the same topics as the targets) to the 60 files, keeps the same 50 queries and the shipped threshold 0.60. Fair keyword baseline (`eval.rs`): any query word may match, Snowball English stemming, stop words dropped, BM25 over the file texts (screenshots: the drawn text, not the OCR output, which favours the baseline).

| 2,060 files | holdout 20 top-1 / top-5 | all 50 top-1 / top-5 |
|---|---|---|
| existing content search (all words must match) | 0 / 0 | 0 / 0 |
| fair keyword baseline | 6 / 11 | 14 / 21 |
| keyword + semantic, 0.60 | 12 / 14 | 28 / 33 |

Semantic is clearly better on these queries (28 against 14 right-file-first, 33 against 21 in the first five), which were written to describe content in other words; that is the case semantic search is for, not a measure of everyday queries. Where it is not: 17 of 50 queries still miss the top 5, 8 of them screenshots (short OCR text scores under 0.60); the fair baseline has the right file in its top 5 for several queries semantic misses (including "making a strong drink with a french press", "parcel arriving this evening", "relocating: how to pack..."); with the distractors, off-topic queries get results at 0.60 (4 of 4; 1 of 4 at 0.70, where tune top-5 falls from 19 to 10); the tune-set rule would now pick 0.70, the default was left at 0.60 and is editable. The semantic index of 2,060 files took 21.9 s at full speed.

Real memory (`bench memory`, release `lookout.exe`, 2,060 files in a data folder, single runs, private working set, MB): **while indexing** (150 s after launch, 10% duty): lookout.exe 12.5, helper 63.9, WebView2 70; combined 146.3 (the helper is a child process, so the bench counts it). **At idle with the plugin on** (helper gone): lookout.exe 9.5, combined 79.6. **Plugin off, same files**: lookout.exe 6.9, combined 89.0. The daemon's own change is about **+2.6 MB** (the indexer thread and client, with no vectors); the combined totals differ the other way because one WebView2 process varied by about 12 MB between runs, so only the lookout.exe rows are comparable. Not repeated; three runs would be needed for a spread. Bench output said "frontend not ready 10 s after launch" in one run; the numbers were still taken.

Scale (`eval scale <assets> 100000`, generated random unit vectors, release): `vectors.log` 41.3 MB; reading, decrypting and parsing it 170 ms; brute-force scan 9.3 ms median (11.2 max) on one thread; helper started cold through the host, answering status (process start, hashing 56 MB of files, model load, vector load) 551 ms; **cold first query 484 ms** (process to answer, model loaded again after a restart); warm query 13 ms median, 15 max; helper private working set 113.5 MB with the vectors loaded, 119.8 MB after the first search. Random vectors give no hits above 0.60, so result building was not exercised.

OCR twice, not implemented: the content store keeps only a preview, so the vector indexer OCRs an image again. A one-time fix needs the OCR text kept somewhere: (1) add a stored, length-capped field with the *masked* OCR text to the content store, only for image documents; (2) the semantic indexer reads that field instead of calling OCR; (3) screenshots indexed before the change need one re-OCR, and the tantivy schema change means rebuilding the content index (or a migration); (4) disk grows by up to about 4 KB per screenshot, encrypted like the rest. Not small enough to do here, since it changes the on-disk index format.

## Phase 4 (plugin host, clipboard history, file tools)

Protocol, layout and the honest list of what is and is not enforced are in `docs/plugins.md`; this section records the choices.

- **Framing.** Newline-delimited JSON-RPC 2.0 on stdio (the brief says only "JSON-RPC over stdio"). Lines over 4 MiB, invalid JSON, a missing `"jsonrpc":"2.0"` or an answer with neither `result` nor `error` count as garbage and kill the plugin. `undo` takes `dry_run` (an addition to the brief's method list): the gate must show what an undo does before it asks for confirmation. `query` may answer `{select: {text}}`, which makes the host search names and call again with at most 8 `candidates` (that is how "files the user picked" reaches a plugin without the plugin reading the index).
- **Risk is decided by the host.** `max(plugin's request in get_actions, risk in preview, manifest floor)`; the floor is `confirm` for any `fs_write`, `spawn` or `network` entry and `dangerous` for a wildcard `fs_write`. A plugin cannot lower it. `execute`/`undo` on the host are functions that need the gate's `Authorized`, and anything a plugin sends other than the `items_changed` notification is refused and counted. A plugin item is the only thing its own actions accept (`Target.origin`), so the webview cannot aim a plugin action at another file or another plugin. Tests: `core/tests/plugins.rs` (crash, hang at startup and in a query, garbage, a 5 MB line, a rogue plugin that sends `execute` requests and notifications, risk floor, run without confirm, confirm without present, instant confirm, stale confirmation, paths the host did not hand out, Job Object child-process limit, idle stop, restart) and `plugins/files-tools/tests/host.rs::with_both_bundled_plugins_off_search_actions_and_undo_still_work` (both bundled plugins off: search, `open`, kill-port and its undo work, and no plugin process ever exists).
- **Lifecycle.** Off and unapproved by default; turning on needs the permissions to be shown and accepted (stored as a fingerprint of id, entry, args, permissions and `background`, so a plugin that asks for more must be approved again). Started on first use; stopped after 60 s idle; killed on timeout, garbage or crash; the next use starts a new process; after 3 failures in a row the host waits 2, 4, ... up to 60 s. The Clipboard plugin is `background`: it must be running to record, so it is started when turned on and restarted by the supervisor thread (250 ms tick) after a crash, instead of lazily. Timeouts: initialize 5 s, query 1.5 s (a busy plugin is skipped, not queued), preview 5 s, execute 60 s, undo 30 s.
- **Enforced vs not.** Job Object per plugin: kill-on-close, no child processes unless `spawn`, no clipboard unless `clipboard`, 1 GiB. Not enforced: file access (no AppContainer), network (needs firewall rules with admin rights or an AppContainer), and a plugin may do work in `preview`. The small gap between process creation and job assignment is not closed. See `docs/plugins.md`.
- **Clipboard.** Text only. Opt-in by turning the plugin on. Polls `GetClipboardSequenceNumber` every 400 ms and reads only when it changed and Lookout is not paused (text copied while paused is skipped for good, also after resuming). Secrets go through `content/secrets.rs::mask` before anything is stored, and **the stored text is the masked text**: the original of a masked clip is not kept anywhere, so "copy" gives back the masked text (the preview says so). Stored in `plugins/com.lookout.clipboard/clips.bin`, sealed with the same key as the index (follow-up: the plugin no longer gets the key file; the host gives it a key derived from the master key and its id, `crypto::derive_plugin_key`, at `initialize` only; clips encrypted with the master key by the first version are not readable and were dropped). Settings: `max_clips` (default 100, at most 5000), `retention_hours` (default 168); clips over 20,000 characters are not stored; the same text again moves to the top. "Clear history" is `clip clear`, a `confirm` action without undo that deletes the file. "Delete my index" also deletes the plugins' data folders (their data was sealed with the deleted key).
  - **Do-not-record formats (from Microsoft's "Clipboard Formats" page, learn.microsoft.com/windows/win32/dataxchg/clipboard-formats).** Three registered formats: `ExcludeClipboardContentFromMonitorProcessing` (if present, nothing may go into clipboard history or sync), `CanIncludeInClipboardHistory` (DWORD, 0 = keep out of history, 1 = allow) and `CanUploadToCloudClipboard` (DWORD, 0 = do not sync; Microsoft says it does not govern local history). All three are obtained with `RegisterClipboardFormat`. Lookout skips a clip when the first is present or either DWORD is 0 (skipping on `CanUploadToCloudClipboard` = 0 is stricter than required). Also honoured but **not in Microsoft's documentation**: `Clipboard Viewer Ignore`, the older convention password managers still set. Checked against real clipboard data by an `#[ignore]` test (it overwrites the system clipboard): `cargo test -p lookout-clipboard -- --ignored`; it passed once on this machine. Not verified against an actual password manager.
  - Not done: images, files, smart paste.
- **File tools.** Verbs: `compress`, `rename`, `strip`; no PDF. Compress uses Windows' image codecs (WinRT `BitmapDecoder`/`BitmapEncoder`, no image crate): the result is always a new JPEG `<name> (compressed).jpg` (alpha dropped), found by bisecting JPEG quality (7 steps) and, if quality 0.05 is still too big, by scaling down in 8 steps to 12%; KB = 1024 bytes. Strip metadata copies a JPEG or PNG byte for byte minus EXIF, XMP, IPTC and comments (JPEG APP1, APP3 to APP13, APP15, COM; PNG tEXt, zTXt, iTXt, eXIf, tIME and unknown chunks), keeping ICC profiles, JFIF, Adobe and animation chunks, into `<name> (no metadata).<ext>`. Rename acts on the regular files directly inside one folder (at most 500, sorted by name, extensions kept); `{n}` is zero padded, `{name}` is the old stem; it refuses invalid or reserved Windows names, duplicates and clashes with files that are not being renamed, renames through temporary names so swaps work, and rolls back on failure. Compress and strip never overwrite, and undo deletes only the copy it made (and only if it still has the recorded size); rename undo refuses if an old name is taken again. The "live preview" is the result row (first three renames, or the reason it cannot work), which changes as the pattern is typed, and the full list on the confirmation card. All three are `confirm`.
- **Plugin panel** (`Ctrl+,`, below the privacy settings): permissions are listed before "Allow these permissions and turn on"; per-plugin settings (clipboard: `max_clips`, `retention_hours`) and the last error. It was type-checked and built, not clicked through in the running app.
- **Dependencies.** No new crate. New Cargo features on crates already in the tree: `windows-sys` `Win32_System_JobObjects` and `Win32_Security` (core, for Job Objects), `Win32_System_DataExchange` and `Win32_System_Memory` (clipboard plugin); `windows` `Foundation_Collections` and the imaging features (files plugin). The plugin crates depend on `lookout-core` (secrets masking, crypto, the SDK loop), so each plugin executable contains core's code. `png` is a dev-dependency of the files plugin (already one of core) to generate test pictures. No network code was added.
- **Not done / known gaps.** No capture plugin, no semantic search. Plugins are not in the Tauri bundle yet (Phase 6; `scripts/stage_plugins.ps1` copies them next to `lookout.exe` for a manual run). One default action per plugin result (the Tab action list is still unbuilt). A verb acts on one file or one folder, not on a selection of several. The plugin panel shows the last error, not a log. Of the Job Object limits only the child-process limit is tested; the clipboard UI restriction and the memory cap are set but not tested.
- **Memory** (`bench memory`, release build, 1 run of 120 s each, empty data folder so no index, private working set of `lookout.exe`, its `msedgewebview2.exe` processes and now also any `lookout-*.exe` plugin processes; budget 150 MB): (1) both plugins installed but **off** (the default): 77.4 MB, no plugin process; (2) Clipboard **on** and running (it is a background plugin), Files tools on but not started (it starts on first use): 70.6 MB, of which `lookout-clipboard.exe` is 0.4 MB. The 7 MB difference between the runs is WebView2 variation (the same kind of spread as Phase 0, 60 to 68 MB), not the plugin. (3) `lookout-files-tools.exe` alone, started and initialised, measured separately with the Windows counter `Working Set - Private`: 0.5 MB (working set 4.8 MB); it was **not** measured while compressing a large picture (the decoded pixels live in that process and would add the picture size times a few). So "both plugins running" is about 1 MB on top of the app, from separate measurements of the parts, not one measurement of all three running together. One run each, on the machine used for the earlier phases; the real clipboard was being watched during run (2).

## Phase 3 (content search, OCR, time filters, privacy controls)

- **Encryption at rest.** One random 256-bit key, stored only as a DPAPI blob (`CryptProtectData`, current-user scope; the entropy argument is a public constant, so it protects against other users and stolen disks, not against code running as the same user) in `lookout.key`. Three artifacts, three constructions:
  - `meta.db` (frecency **and the undo log**, so command lines and working folders are encrypted, as Phase 2 promised): SQLite runs in memory and the whole database is sealed (ChaCha20-Poly1305, 64 KiB authenticated chunks, last-chunk flag against truncation) and atomically swapped into the file after every write. **Not SQLCipher**: its Windows build needs OpenSSL and Perl, which would burden CI and users' builds. Cost: every write rewrites the file, fine for a database of kilobytes, wrong for one of hundreds of megabytes. A plaintext `meta.db` from Phase 2 is read once and rewritten encrypted. If the undo log cannot be written the action does not run (unchanged).
  - `names.idx`: sealed snapshot of the name index, written in the background (at most every 10 s, only when changed, not while paused) and on a normal stop. Saves stream through the cipher, no second copy in memory.
  - `content/`: a tantivy `Directory` that stores each file as `nonce || ChaCha20(content)`. ChaCha20's keystream is seekable, so tantivy still reads arbitrary ranges. **This part has confidentiality but no integrity check**: a person who can write to the folder can corrupt the index (tantivy's own checksums catch most damage) but not read it. Unreadable or incompatible indexes are rebuilt, since they are derived data.
  - If the key file cannot be unwrapped (other Windows user, other machine, damaged), `Storage::open` does not delete anything: it renames `meta.db`, `names.idx`, `content/` and `lookout.key` to `*.unreadable`, starts with a new key and the shell shows a dialog saying the index could not be unlocked and was set aside. The set-aside files are deleted by the next process start that opens normally (the user has been told by then) and by "Delete my index". The same applies if a valid key cannot open the database.
  - Not protected: `settings.json` (user choices, includes folder names), the process's memory while running, and anyone who can run code as the same Windows user (DPAPI's model). The key is zeroed on drop on a best-effort basis (no `zeroize`).
- **Persistent name index.** Snapshot of folders and files (names and modified times, not frecency, which comes from `meta.db`). It is trusted only if made for the same roots and exclusions (a fingerprint is stored inside the encrypted file), so a newly excluded folder never shows up from an old snapshot. The snapshot is served immediately; the startup crawl then builds a fresh index and swaps it in (the existing rescan path), which repairs everything that changed while Lookout was off. So **startup briefly holds two indexes** (the memory cost measured for rescans in the Phase 1 follow-up); idle memory afterwards is unchanged. Not done: reconciling in place without the second copy.
- **Content index** (`core/src/content`). tantivy 0.27 schema: lowercase path key, stored path, `body` (indexed, not stored), 240-character stored preview, kind (`text`/`ocr`), modified time (fast field, used for time ranges). All query words must match; the last word also matches as a prefix (so results appear as you type). Content matches score 0.6 times a normalised BM25 so they never outrank a good file-name match; a file found both ways appears once (best score). Text files are read only up to 1 MiB. The writer exists only during a batch and is dropped after each commit (batches commit every 50 documents, when the gate closes, and at the end). **Not extracted by the core: e-mail. Word, Excel, PowerPoint and PDF come from the Office helper plugin (see below)**. Extensions read: `txt md markdown log csv tsv json xml yaml yml toml ini cfg conf html htm rs py js ts tsx jsx java c h cpp hpp cs go rb php sh bat ps1 sql tex rst org srt vtt`.
- **What is never indexed.** Folders in `excluded_folders` and the built-in names (names, contents and OCR); symbolic links; files that commonly hold secrets (`.pem .key .pfx .p12 .ppk .kdbx .jks .gpg .asc .env`, `.env*`, `id_rsa` and friends, `.netrc`, `credentials`) are never even opened. **Masking** (`content/secrets.rs`): before any text reaches the index (file text and OCR text alike) these are replaced with `[masked]`: private key blocks; AWS, GitHub, Slack, Stripe/OpenAI-style, Google API keys and JWTs; values in `password/secret/token/api_key = ...`; digit runs of 13 to 19 that pass the Luhn check; random-looking tokens of 32+ characters (entropy >= 4.2, so git hashes survive). It is pattern based and best effort, not a guarantee. Tests assert that a masked secret cannot be found by search, is not in any preview, and is not in any byte of the index files. The clipboard (Phase 4) is expected to reuse the same detector.
- **"Idle" and CPU.** `GetLastInputInfo`: content extraction and OCR start only after `idle_secs` (default 10) without keyboard or mouse input, and stop (at the next file boundary) when the user returns. The worker also keeps to a 10% duty cycle (`crawl_duty`). **The file-name crawl is not idle-gated** (still only duty-cycled and pause-aware, as in Phase 1): it is cheap, reads no file contents, and gating it would make folder search stay empty for tens of seconds after the first-run choice. This is a deliberate reading of "indexing runs only when the user is idle".
- **Pause** (tray item, `Ctrl+Alt+P` via `pause_hotkey`, panel checkbox) is one shared flag. It holds back the name crawl, watcher updates, rescans, the snapshot saver, content extraction and OCR. Every unit of content work first passes the gate. **The file already being read or OCR'd finishes** (a Windows OCR call cannot be cancelled); anything already extracted is committed once when the gate closes. Tests: paused start extracts nothing and OCRs nothing, files created while paused are not read, a pause triggered in the middle of a 120-file batch freezes the counters, resume continues, user activity blocks work.
- **OCR: Windows.Media.Ocr only; no Tesseract.** It works on this machine (English language pack): generated BMP and PNG screenshots with known text are read correctly by the unit tests and by the end-to-end test, so Tesseract was not needed (it would add a native dependency and language data). Where no OCR language is installed `TryCreateFromUserProfileLanguages` fails, the engine is reported unavailable, images are skipped without being marked done, and the OCR tests print SKIPPED. That means CI (`windows-latest`) may skip them, and **it cannot be told from the CI log whether it did**: a skipped test passes, and its SKIPPED message goes to captured stderr that cargo test does not print for passing tests (the log of the first Phase 3 run was also not yet available when this was checked). So the OCR tests prove OCR only on a machine that has an OCR language; on CI they may be empty passes. The fake-OCR tests (masking, pause, off switch) always run. Images wider or taller than the engine's maximum are skipped (not scaled); an image that cannot be decoded is recorded empty so it is not retried on every scan. OCR accuracy on my 5x7 pixel-font fixtures is imperfect (it read "INVOICE 4821" and "MEETING AT NOON" but misread "HOLIDAY PLANS" and "PAID"); the tests use text it reads reliably. Real screenshots use real fonts and were not tried (no real files are read).
- **Time filters** (`timefilter.rs`, `chrono`, local time zone, weeks start Monday): `today`, `yesterday`, `this week|month|year`, `last week|month|year` (previous calendar period), `past week|month|year` and `last N days|weeks|months|years` (rolling, ending today; month = 30 days, year = 365), a month name with an optional year (`march`, `june 2025`: the most recent such month that has started), with an optional `in/from/during/since/of` in front. A lone month word (`march`) stays an ordinary word unless a preposition precedes it, because it may be a file name; `march madness` uses the filter. Only the first phrase is used. The window filters name results by modified time and content results through the index; a query with only a time phrase lists the most recently modified entries. Not done: "2 weeks ago", `since 2025`, `before/after`, times of day, "this morning".
- **`screenshot with <text>`**: a leading `screenshot(s)|image(s)|picture(s)|photo(s)` followed by `with|containing|saying|showing|of|that says|that has` turns into `kind:screenshot` plus the rest as text. `kind:screenshot` (or `kind:image`) restricts to OCR hits.
- **Privacy panel.** `Ctrl+,` (and automatically on first run): choose folders (native folder dialog; the bar's hide-on-blur is suspended while it is open), exclusions, pause, delete. Saving restarts search (`Lookout` is replaced in the shell). The webview supplies folder paths; they must exist as directories, and, as with every command, the webview is part of the trusted computing base (see Phase 2). First run is "no folders chosen and the choice never made"; a Phase 2 `settings.json` with folders counts as chosen. The dev flags `--index-root` and `--synthetic-index` count as the choice.
- **Delete my index** removes `meta.db`, `names.idx`, `content/` and `lookout.key`, empties the in-memory index, forgets the folder choice (`index_roots` cleared, `first_run_done` false, so the chooser returns) and keeps the rest of `settings.json`. It also deletes frecency and the undo log, since they live in the same encrypted database. Services are stopped first and `meta.db` writes are switched off; tests check that nothing remains and nothing is re-created afterwards. The shell then starts a new `Lookout`, which creates a fresh, empty key and database, so a new `lookout.key` exists again straight away (it protects nothing yet). Your files are not touched.
- **Dependencies added** (core): `tantivy`, `chacha20poly1305`, `chacha20`, `getrandom`, `chrono`, `regex`, `windows` (WinRT OCR), and `png` (dev only); rusqlite gets its `serialize` feature. No network code was added.
- **Memory** (private working set, `lookout.exe` plus its `msedgewebview2.exe` processes, same definition as Phase 0; `bench memory`): (1) 1M generated names loaded, idle 120 s, 3 runs: 126.3, 126.0, 126.3 MB (Phase 1 was 125.9 to 126.1; budget 150). `lookout.exe` itself is about 53 MB of that, as before; the full-text reader adds no measurable idle memory. (2) During a content and OCR batch (generated corpus of 3,000 text files of about 4 KB and 60 BMP screenshots, indexed right after launch with `idle_secs` 0, sampled every second for 120 s, 2 runs): peak combined private working set 94.1 and 95.1 MB, 85.6 and 86.8 MB at 120 s. The batch itself took about 62 s. This corpus has no big name index, so it shows the content batch's cost (about 10 MB over the roughly 80 MB baseline) rather than the sum with a 1M-name index; the combination is measured in the follow-up below. (3) CPU of `lookout.exe` during that batch, in 5 s windows: 5.8 to 13.8%, mostly 9 to 13% of one core (so a little over the 10% target; the figure includes startup, the name crawl and the WebView hand-off), then 0.0 to 0.9% once finished. The duty cycle caps wall-clock busy time at about 10% but the Windows OCR call can use more than one thread inside it. **Follow-up measurements (sampled every 250 ms; same definition, budget 150 MB):** (a) 1M generated names plus the same content and OCR batch at the same time, 2 runs: peak 144.2 and 142.7 MB, 132.7 and 133.6 MB at 120 s; passes with about 6 MB to spare. (b) Startup with a persisted snapshot while the fresh crawl builds a second index (1,000,000 real empty files named `file N.txt`, snapshot 7.1 MB, content indexing off, 90 s): first sample 36.6 MB, **peak 149.8 MB at 44 s** (0.2 MB under budget), 115.8 MB at 90 s after the swap. The names in that tree are shorter than typical, so a real 1M-file profile will likely exceed 150 MB at the swap (the Phase 1 rescan estimate was +37 to +47 MB over the idle size). **Fix (implemented): `snapshot_max_entries`** (setting, default 300,000 entries, files plus folders; the count is stored in the encrypted snapshot header). A snapshot above the limit is not loaded, so there is never a second big index at startup: **search starts empty after launch above that size** and fills as the startup crawl runs (names appear progressively; with frecency applied after the crawl). Below the limit behaviour is unchanged. 0 disables snapshot loading. Test: `a_snapshot_above_snapshot_max_entries_is_not_loaded_and_the_crawl_fills_the_index`. (Found while testing this: a startup crawl interrupted by a stop used to mark the index changed, so the final save could replace a good snapshot with a partial one; it no longer does.) Re-measured once with the fix (same 1M-file tree, 90 s, 250 ms samples): peak 126.8 MB at 40.8 s (was 149.8 MB), 114.9 MB at 90 s.
- **Known gaps.** No integrity protection for the content index files (above). The content index is not compacted or size-limited. The idle gate polls every 100 ms. The webview, not the backend, validates nothing beyond "is a directory" for folder choices. The live end-to-end script (`scripts/live_e2e.mjs`) was not re-run for Phase 3 and the privacy panel was type-checked and built but not clicked through by me (no GUI automation of the native folder dialog), see the report.

## Phase 2 (action engine, preview/confirm, undo log, kill port)

- **How an action runs: a ticket protocol enforced in the backend** (`core/src/actions/gate.rs`). `prepare` looks at the real state and returns a single-use ticket plus the preview; `present` is called by the UI once the card is on screen; `run` executes `safe` tickets only; `confirm` executes any ticket but only after `present` and at least 350 ms later (a held key or a script calling both back to back cannot confirm). `run` on a `confirm`/`dangerous` ticket fails with `ConfirmationRequired` and leaves the ticket usable. Tickets expire after 60 s, at most 16 live at once. `Action::execute` needs an `Authorized` value that only the gate can construct, so no other code path in the crate can call it. The webview can name only an action id and a result id from the latest update; paths and ports come from the backend's own items (`Lookout::target`), so `prepare_action("open", "file:C:\\Windows\\System32\\cmd.exe")` is refused. Before executing, the gate plans again and compares a fingerprint with the previewed one; a different process on the port, a replaced `.exe`, or a changed risk gives `Stale` and nothing runs. Tests: `gate::tests::confirm_and_dangerous_actions_cannot_be_run_without_the_confirm_step` (the bypass test: wrong call, no `present`, instant confirm, made-up/cancelled/reused tickets, both risk levels), `a_confirmation_never_applies_to_a_state_that_differs_from_the_preview`, and `core/tests/kill_port_real.rs`. The same attempts were also made through the real webview commands (below). What this does not defend against: code running inside the Lookout process itself, or a webview that really clicks Confirm. There is no compile-fail test for `Authorized` (that would need `trybuild`).
- **Undo log** (`undo_log.rs`): table `undo_log` in `meta.db` (own connection next to frecency): time, action id, item ids, params (the plan snapshot), undo token, status, detail. The row is written as `started` before the action runs and the action does not run if that write fails; it becomes `executed`/`failed` afterwards, and a row still `started` at the next launch becomes `interrupted`. Undo (`Ctrl+Z` with an empty box, or the Undo button after an action) reverts the newest `executed` row with a token and is itself a ticket that needs confirmation, because restarting a program starts a process; it marks the row `undone`/`undo_failed` (no separate row). `meta.db` is not encrypted until Phase 3, so anyone who can write that file can change a stored restart command; the card always shows the exact program, command and folder before it is confirmed.
- **Kill port** (`kill_port.rs`): `kill 3000`, `kill port 3000`, `stop :3000`, `free port 3000` produce one result. The result's subtitle names the process as a hint only; pressing Enter calls `prepare`, which reads the TCP listener table (`GetExtendedTcpTable`, IPv4 and IPv6) and then each listening process's program, full command line and working folder (`sysinfo`), so the card shows what is running at that moment. Only TCP listeners are considered (not UDP, not established connections), and only the process that owns the socket is stopped, not its parent (stopping `node` leaves the `npm` that started it). Risk is `confirm`; it is `dangerous` when the program is in the Windows folder or its details cannot be read (another user, elevated). Refused outright: PID 0 and 4, `csrss`, `lsass`, `services`, `winlogon`, `wininit`, `smss`, `dwm` and similar, Lookout itself and its own WebView2. The stop uses one handle for both the identity check (pid plus creation time) and `TerminateProcess`, so a reused pid cannot be hit; `Failed` is reported if Windows refuses (elevated process).
- **Restart as undo** works only when the command line, program path and working folder were all captured. It starts the same program with the same arguments in the same folder, without a console window, as a child of Lookout, with Lookout's environment (environment variables are not captured, so a dev server that relied on variables set in its terminal will not behave the same). The preview says so. Undo refuses if the port is in use again or the program or folder no longer exists, and reports "started but not listening yet" if the port does not open within 10 s. A process whose details could not be read gets "This cannot be undone" on the card.
- **Open is an action with a risk level** (`open.rs`), by allowlist. Safe (one step, bar closes, frecency recorded): folders, Start Menu apps, and files whose extension is in `SAFE` (documents `pdf doc docx odt rtf xls xlsx ods csv ppt pptx odp epub`, text `txt md log json xml yaml yml toml tsv`, images `png jpg jpeg gif bmp webp tif tiff ico heic`, audio `mp3 wav flac ogg m4a aac wma`, video `mp4 mkv avi mov wmv webm m4v`, archives `zip 7z rar tar gz tgz bz2 xz`). Everything else needs confirmation, including no extension, `.url .appx .msix .iso .chm .docm .xlsm .svg .html` and all code types (`.exe .bat .cmd .js .vbs .msi .ps1 .scr .hta` and more; those read "Run ..." on the card, others "Open ... (unrecognised type)"). The check is on the real file at that moment (a result the index calls a folder that is now `x.exe` is confirm), ignores case, trailing dots and spaces (`setup.exe.`), and treats any `:` in the file name (NTFS stream `a.txt:evil.exe`) as confirm. A confirmed file is pinned by size and modified time, so replacing it after the preview cancels the run. Opening is not undoable.
- **`open` crate switched to `shellexecute-on-windows`; kept.** Measured here against the PowerShell launcher, one run each, 9 file names (`plain`, `R&D plan`, `a^b`, `100%`, `[1] x`, `résumé 日本`, `it's (v2) !`, `-dash`, `/e`, each a `.bat` that writes its own `%~f0` to a marker file): all 9 ran under both launchers; the exact path was confirmed for the 8 names without non-ASCII text (`cmd` cannot write the CJK name back, so for that one only "the right file ran" is shown). `that_detached` returned in 100 to 173 ms with ShellExecute and 258 to 297 ms with PowerShell; time until the file's own marker appeared was 216 to 362 ms against 956 to 2,242 ms. A folder opened as the folder itself (not its parent) in both (166 vs 284 ms to the Explorer window); a `.txt` named `R&D notes 100%.txt` opened in Notepad with that title in 665 vs 1,490 ms. ShellExecute receives the path as a single `lpFile` and no parameters, so nothing is parsed by a shell. Not tried: a file type with no handler, UNC paths, paths over 260 characters, an elevated target. The Phase 1 description of the PowerShell launcher below is superseded; the metacharacter test still holds (it checks the path handed to the launcher).
- **Live check of the real app** (release `lookout.exe` driven through the WebView2 debugging port by `scripts/live_e2e.mjs`, victim `core/examples/test_listener`): 25 of 25 checks passed (confirms use real input events through the debugging port: Input.dispatchKeyEvent and dispatchMouseEvent; synthetic calls only for the refusal tests, plus a check that a synthetic click on Confirm is ignored). They cover search showing the real PID, the card text, focus on Confirm, `run_action`/`confirm_action` refusals from the webview (not presented, instant confirm, unoffered port, arbitrary path), Enter/Space on the window not confirming, button confirm stopping the process, quitting and relaunching Lookout, `Ctrl+Z` offering the restart, the restart listening on the same port, a document opening in Notepad with no card, a `.bat` showing a card, `Esc` cancelling it, and Confirm running it. The confirm input is real browser input but not a physical keyboard or mouse.
- **Tests never kill real processes.** The victim is `core/examples/test_listener.rs`: it only listens on a loopback port and exits by itself after two minutes. Every kill targets a pid the test started, found through the port the test picked. Cases that must not touch a real process (Windows processes, `svchost`, Lookout itself) use a fake `ProcessBackend`.
- **UI.** Enter on a result starts its default action. A `confirm` card shows the preview, warnings and Cancel/Confirm; focus starts on Confirm, and on Cancel for `dangerous`. With a card open the window ignores Enter, so only the focused Confirm button confirms; `Esc` closes the card (the bar stays). `Ctrl+Z` is the action undo only when the search box is empty, otherwise it stays the text field's own undo. The card is not color-only (a "Needs confirmation" or "Dangerous" label). Not built: Tab action list and reveal in folder (`Ctrl+Enter`); they were not on this phase's list.
- **What the gate does and does not protect against.** It protects against accidents (a stray Enter, key repeat) and scripted fast calls (prepare, present, confirm back to back). It does not protect against a compromised webview: `present` is only the webview's claim that the card is on screen, and a webview that waits 350 ms can call every command itself. The UI ignores confirm events that are not `isTrusted`, and the Content-Security-Policy keeps foreign script out, but both are UI-side. The real boundary is that only items the backend produced can be targeted and that previews come from the live state. Command lines in the undo log are stored unencrypted until Phase 3; then encrypt them with the rest of `meta.db` and consider masking secret-looking arguments (tokens, passwords, keys) in the log and on the card.
- **Content-Security-Policy** (`tauri.conf.json`): `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src ipc: http://ipc.localhost`. No inline script or `'unsafe-inline'` was needed (Svelte compiles to an external module and stylesheet). `ipc:` and `http://ipc.localhost` are what Tauri 2 uses for commands; I did not test the app without them. The live check (25 checks, 0 console errors or CSP violations) ran against this policy.
- **Dev flag `--data-dir <path>`** moves `settings.json` and `meta.db` (frecency and undo log) away from the user's folder; the live check uses it.
- **Action commands are `async`** in the Tauri shell so a stop or restart that waits (up to 5 s to stop, 10 s for a restart to listen) does not freeze the window.
- **Scheduled rescans are off by default, so changes the file watcher misses without reporting an error are repaired only when Lookout is restarted (the index is rebuilt on every launch).**

## Phase 1 follow-up (measured on an i5-12400F: 6 cores, 12 threads; NVMe, Windows 11)

- **How file open worked in Phase 1 (`open` 5.4.5, default features, from its source in the cargo registry). Superseded: Phase 2 enables `shellexecute-on-windows`.** `open::that_detached` does not call ShellExecute and does not use `cmd /c start`. It tries `powershell.exe -NoProfile -NonInteractive -Command <script>` first, with the target passed as data in the environment variable `OPEN_RS_TARGET`; the script runs `Invoke-Item -LiteralPath` if the path exists (otherwise `Start-Process`). If that launcher fails within 250 ms it falls back to `explorer.exe <path>` (a path starting with `-`, `/e`, `/n`, `/separate`, `/root,` or `/select,` is prefixed with `.\` so Explorer cannot read it as an option). ShellExecute is used only with the crate's `shellexecute-on-windows` feature and `cmd /c start` only with its `insecure` feature; Lookout enables neither. Consequences: `&`, `^` and `%` in a file name are never interpreted by a shell, and `[` or `*` are not treated as wildcards; the cost is starting a PowerShell process on every open (typically a few hundred milliseconds). The test `names_with_shell_metacharacters_are_found_and_open_to_the_exact_path` checks that `R&D plan.txt`, `a^b.txt` and `100%.txt` are indexed, found by the obvious query, not mistaken for a calculation, and that `open_target` returns the exact path. It does not launch a program.
- **Scheduled rescan as the watcher-loss fallback.** `notify` 8.2.2's Windows backend ignores the byte count that `ReadDirectoryChangesW` uses to signal a buffer overflow (`windows.rs`, `handle_event`, parameter `_bytes_written`) and never raises a rescan flag (only its inotify and FSEvents backends do). Lost events therefore cannot be detected on Windows. Instead the index is rebuilt from disk every `rescan_hours` (default 6, 0 disables) and swapped in (`index_service.rs`, `rescan`); a watcher error also triggers one, and `IndexService::request_rescan` triggers one on demand. During a rescan queries keep using the old index and peak memory is two indexes (measured below); pausing holds a rescan until resume. **Default: no scheduled rescan.** `rescan_hours` defaults to 0, so a rescan runs only after a watcher error or `request_rescan`; setting `rescan_hours` to 24 is the opt-in. Measured: a burst of 100,000 new files created at 12,558 files/s by 8 threads was fully indexed by the watcher alone (0 missed), so overflow is a risk the fallback covers rather than something observed here.
- **Memory during a rescan (`bench rescan-memory`, 1,000,000 real files crawled from a temp folder at the default 10% duty, private working set sampled every 250 ms, 246 samples).** The rescan took 50.6 s. This process held 39.6 MB before it, rose steadily to a **peak of 77.4 MB (+37.8 MB) at the moment of the swap**, and returned to 39.8 MB ten seconds later (peak private bytes 93.2 MB). It is a bench process holding only the index, so to compare with the 150 MB budget (combined `lookout.exe` plus WebView2) the +37.8 MB is added to the app's idle total. With the generated 1M-name index the app idles at 126.0 MB (WebView2 about 72.7 MB of that), and its names are longer than the file names in the temp tree (19 vs about 13 characters), so its second index is larger: expected peak about 126.0 + 47 = **about 173 MB**. With the temp tree's own index size (WebView2 72.7 MB plus about 43 MB for `lookout.exe`, which is the bench's 39.6 MB plus the app's roughly 4 MB of other state) the estimate is 115.7 + 37.8 = **about 153.5 MB**. Both are over 150 MB, so the default was changed as above. These are sums of separately measured parts, not a measurement of the whole app during a rescan (the app has no way to trigger one on demand). A rescan after a watcher error has the same peak; it is rare and short.
- **Watcher events are applied after 200 ms of quiet or 2 s at most.** Before, a continuous stream of events (a build writing files) would never be applied. Test: `busy_event_streams_are_still_applied_within_the_max_batch_age`.
- **Crawl time, 1,000,000 empty files in 20,021 folders on a warm file cache** (`bench crawl`): 8.2 s unthrottled (122k files/s; 3.1 s when run again with everything cached), and **42.2 s at the default 10% duty cycle**, using 10% of one core (4.2 s of CPU in 42.2 s). A user searching every 20 ms during the 10% crawl saw p50 0.69, p95 1.90, max 3.12 ms. A cold first crawl of real data will be slower, bound by disk metadata reads; that was not measured because it needs real folders.
- **Locking.** The index is `Arc<RwLock<NameIndex>>` (std; Windows SRW lock). There is no copy-on-write. A query holds the read lock for the whole scan (`FilesSource::query`, 0.5 to 6.5 ms at 1M names, up to 35 ms single-threaded for `a`). Writers (crawl batch per folder, watcher event, `shrink_to_fit` after a crawl) take the write lock briefly. Writer hold times at 1M names: add one file about 0.00 ms; the duplicate check that precedes it (`contains_file`) 1.4 ms p50, 2.1 p95; removing a file 1.3 ms; removing a folder tree 6 ms; `compact()` 15 ms at 47% dead; `shrink_to_fit` 0.1 ms. Consequence: while a 1M-name index is being updated by the watcher, throughput is about 700 events/s because each one scans the name arena. The rescan swap is a replace under the write lock.
- **Known problem: writer starvation under back-to-back queries.** With one reader scanning continuously (no gap between queries), a writer waited p50 69 ms, p95 390 ms, max 982 ms for the write lock (`bench locks`). With 4 readers it was p50 1.8, p95 6.8, max 14 ms. **Decision: leave the lock as it is.** The 1-reader result (p50 69 ms) comes from a reader that starts its next scan the instant the previous one ends, thousands of times per second; real typing never does that (keystrokes are tens of milliseconds apart, each scan is 0.5 to 6.5 ms, and the previous scan is cancelled when the next key arrives). Index updates are therefore not expected to stall in practice. A writer-preferring lock is not planned; revisit only if indexing is seen lagging under heavy search use.
- **Benchmark corpus.** File names: 1M generated names, length in characters min 10, p50 19, mean 18.8, p95 24, max 31 (real folders have a longer tail, which makes scans proportionally slower). Mix: 6 name patterns, 120 words, 17 extensions weighted toward pdf/jpg/docx/txt/png, 40% capitalised, about one folder per 40 files at most 6 levels deep.
- **Threads.** One scan uses `min(hardware threads, 8)` threads once the index passes 200,000 entries (here 8 of 12); the engine adds one short-lived thread per source. First-results p95 across the 10 benchmark queries, in ms: 8 threads 0.87 to 10.53 (worst `a`, max 23.9 in this run); **4 threads 1.27 to 11.89** (`a` 11.89, `re` 6.81, the rest at most 2.60); 1 thread 1.45 to 38.29 (`a` 38.29, `re` 15.61, the rest at most 4.79). All within the 50 ms budget; the single letter `a` is the only query where the thread count matters. Run-to-run spread is real: the first Phase 1 run measured `a` at p95 6.54 ms with 8 threads, this one 10.53 ms.
- **Frontend update filtering verified live.** Against the running app, an update for generation 0 was ignored, the UI accepted exactly its current generation (2) and rejected generation 1 (`onUpdate` in `App.svelte`).

## Phase 1

- **Name index is a lowercase arena plus SIMD substring search, not an FST or trie.** Section 6 names FST/trie as the default. Those structures answer prefix and automaton queries, but users expect a match in the middle of a name (`report` finds `Q3 annual report.pdf`). A single `memmem` pass over a 25 MB arena finds those, and measured at 1M names it is far inside the budget (below). Costs: the scan is linear, so time grows with the number of names; at 1M it is 0.5 to 6 ms. Revisit if indexes of 10M+ names matter.
- **Query-time numbers** (`bench query`, 1,000,000 synthetic names, 12 hardware threads, 100 repetitions per query, ms): index search p95 0.53 to 6.36; keystroke to first results through the whole engine (submit, source threads, merger, sink) p50 0.70 to 6.36, p95 0.86 to 6.54, max 7.36. Worst case is the single letter `a` (about a million matches, all scored). Fast typing of an 18-character phrase: last keystroke to first update p50 4.96, p95 5.54 ms, and 0 updates for older generations delivered after the final query began answering. The UI hop (IPC and webview render) is not in these numbers.
- **Idle memory with the index loaded** (`bench memory --app-arg --synthetic-index --app-arg 1000000`, 3 runs of 120 s, combined private working set): 126.1, 126.0 and 125.9 MB, against the 150 MB budget (Phase 0 baseline 60 to 68 MB). `lookout.exe` itself is 53 MB of that (the index is about 49 MB; 48.4 MB of buffers for 1M names). Working set is 396 to 400 MB and private bytes 203 to 212 MB; neither is budgeted. A user with 3M indexed names would exceed the budget, so memory per name (about 49 bytes) is the number to watch.
- **Synthetic data only.** The 1M corpus is generated (`core/src/synthetic.rs`, seeded, never touches the file system). Tests and benchmarks use generated names or temporary folders, never real user files. Real names are less uniform than generated ones, so real-world scan times will differ somewhat.
- **Indexing is opt-in; no default roots.** `index_roots` is empty until the user lists folders in `settings.json`. The brief's first-run folder chooser is Phase 3 ("privacy controls"), so until then file search finds nothing by default. Apps work out of the box.
- **Crawl "idle" is a duty cycle, not idle detection.** The crawl is busy at most about 10% of the time (`crawl_duty`) and stops while paused. It does not yet back off when the user is busy. The first crawl of a large disk therefore takes minutes.
- **The index is rebuilt on every launch** (not persisted). Persisting, with encryption at rest, belongs with the Phase 3 privacy work.
- **Watcher limits.** Create, delete and rename (as delete plus create) are applied after a 200 ms quiet period. A modified file keeps its old modified time in the index, so recency only changes when the file is re-indexed. Symbolic links and junctions are skipped, and a directory removed while indexed is tombstoned together with everything below it.
- **Query syntax is free text plus `kind:`.** Time phrases (`last week`) and action verbs (`kill`, `compress`) from section 7.5 arrive with content search (Phase 3) and actions (Phase 2).
- **No currency conversion.** It is optional in the brief and needs exchange rates, which means network access or a stored cache. Calculator and unit conversion are in.
- **Query generations are numbered by the frontend**, not the backend, so the frontend can reject an update for any generation but its latest without waiting for a round trip. The backend ignores a submit that is not newer than the last one.
- **Frecency lives in SQLite (`meta.db`), unencrypted for now.** It is an exponentially decayed open count with a 14-day half-life, mirrored into the index as one byte per entry after the first crawl. DPAPI encryption at rest is Phase 3.
- **Enter opens; nothing else acts yet.** Opening a file, folder or app with its default handler is part of Find. Reveal in folder, copy, undo and every other action wait for the Phase 2 action engine. `open_item` only accepts ids that were in the latest update the backend sent.
- **Ranking weights** are `match 1.0, frecency 0.6, recency 0.2, semantic 0.0`, configurable in `settings.json`. `fixtures/ranking/cases.json` holds 12 known queries and the result that must rank first; a ranking change that reorders them fails `core/tests/ranking_fixture.rs`. Calculator and conversion answers score 100 so they always lead; apps get +0.25 so an app beats a file of the same name.
- **Equal scores tie-break toward the later-indexed entry.** Arbitrary but deterministic.

## Phase 0

- **Brief conflict: hidden prewarmed window (section 6) vs idle RAM < 150 MB (section 8).** Section 6 requires the window to be created at startup and kept hidden, which keeps a WebView2 process tree alive (6 `msedgewebview2.exe` processes in every measured run). That tree dominates idle memory: `lookout.exe` itself is about 25 MB working set. The two requirements cannot both be met under every definition of "RAM".
  - **Measured metrics** (`bench memory`, `lookout.exe` plus all `msedgewebview2.exe` descendants, 2 minutes after launch with the bar hidden): (1) *working set* (`WorkingSetSize`, counts shared pages once per process), (2) *private bytes* (`PrivateUsage`, committed private memory), (3) *private working set* (resident pages not shared with other processes, Task Manager's "Memory" column; read with `QueryWorkingSet`, cross-checked against the `\Process V2(*)\Working Set - Private` counter within 1%). Three runs, combined totals in MB:

    | Run | Working set | Private bytes | Private working set |
    |---|---|---|---|
    | 1 | 330.1 | 152.7 | 66.9 |
    | 2 | 323.1 | 147.3 | 60.0 |
    | 3 | 333.1 | 151.2 | 68.4 |

  - **Budget: decided by the owner.** Idle RAM budget is **150 MB** (the original budget of brief section 8), measured as **private working set** summed over `lookout.exe` and all its `msedgewebview2.exe` child processes, 2 minutes after launch with the bar hidden. `bench memory` fails if any run exceeds 150 MB. Measured private working set is 60.0 to 68.4 MB, so the budget is met with about 80 MB of headroom for the Phase 1 index. The earlier decision to raise the budget to 250 MB (based on private bytes of about 150 MB, which is a different metric) is **superseded**. The conflict between sections 6 and 8 disappears once the budget is defined on private working set. Working set (323 to 333 MB) and private bytes (147 to 153 MB) are still reported but not budgeted.
  - **Bench pitfall:** WebView2 processes outlive a killed `lookout.exe`, and the next launch attaches to them, so `bench memory` kills the whole process tree after each run and fails if it finds no WebView2 children.
- **Svelte was chosen from the brief's options.** The brief allows "Svelte or React + TypeScript". Svelte compiles away its runtime, so the bundle is small (about 28 kB of JS now), which suits a window that is created once and kept hidden.
- **Daemon logic must move out of the Tauri crate as it grows.** Today `ui/src-tauri` hosts the hotkey, tray and window logic. From Phase 1 the index, query engine and action engine must live in `core/` crates, with the Tauri crate reduced to a thin shell. Otherwise the code cannot be unit tested (see below), and a future plugin host or headless daemon would have to untangle it from Tauri.
- **Hotkey is ignored until the frontend reports ready.** A show before the page has registered its listener would be lost, so the hotkey does nothing during the first moments after launch. The ready time is logged to stderr. If the frontend has not reported ready 10 s after launch, an error is logged and a dialog says the interface failed to load.
- **Daemon lives in the Tauri crate for now.** The brief describes a daemon and a UI talking in-process. In Phase 0 the Tauri app (`ui/src-tauri`, binary `lookout`) is the daemon host (hotkey, tray, window). Logic that does not need Tauri goes in `core/` so it can be unit tested.
- **No tests in the Tauri crate.** On Windows a Tauri test executable fails to start without an application manifest, so `test = false` is set there and testable code is kept in `lookout-core`.
- **"Pause" is a flag only.** The tray item toggles `PauseState` in core. Nothing indexes yet, so it has no visible effect until Phase 1. The brief also mentions a pause hotkey; it is not added in Phase 0 because the task listed only the tray.
- **Hotkey is configured by editing `settings.json` and restarting.** A settings UI is Phase 6.
- **Hide on focus loss** was added so the bar behaves like a launcher; not in the brief.
- **TypeScript 6, not 7.** `svelte-check` does not yet support TypeScript 7.
- **Latency definition.** `t0` is taken inside the hotkey handler, so OS key-delivery time is excluded. "Visible" means two painted animation frames in the webview, which includes up to ~33 ms of frame wait at 60 Hz.
- **Self-driven benchmark.** `--measure-latency` triggers the show path directly rather than synthesizing key presses, so it is repeatable but skips the OS hotkey dispatch. The hotkey path itself was checked separately with a synthetic Alt+Space.
- **Release profile** uses `panic = "abort"`, thin LTO and stripping to keep the binary small.

## Feasibility: text search in PDF and Office files (study only, nothing built)

1. Office (docx/xlsx/pptx = zip of XML). Cargo.lock has flate2 but NO zip crate; quick-xml 0.42 is only transitive (tauri/plist), not a workspace dependency.
   - zip 9.8.1: MIT, rust-version 1.89, active. Small; pulls flate2/crc32fast (already locked) plus a few small crates. No C dep by default (deflate via miniz_oxide). Unsafe only in leaf crates.
   - quick-xml 0.42: MIT, active, pure Rust, already in the lock. roxmltree 0.21 (MIT OR Apache-2.0): DOM, needs the whole part in RAM, so worse for zip bombs.
   - Smallest set: zip (default-features off, deflate only) + quick-xml streaming. Text lives in word/document.xml (w:t), xl/sharedStrings.xml (t), ppt/slides/*.xml (a:t).
2. PDF. Windows.Data.Pdf only renders pages; it gives no text. Built-in route is render + Windows.Media.Ocr (already used for images).
   - Pure Rust: pdf-extract 0.12 (MIT, on lopdf) and lopdf 0.47 (MIT). Both pure Rust, maintained, but they panic on some malformed files and fail on odd fonts/encodings (must run under catch_unwind or in the helper).
   - Pure-Rust text: typically milliseconds per page. Render + OCR: roughly 0.3 to 1 s per page (not measured here), so a 200-page PDF is minutes of CPU.
   - Failure cases: scanned PDFs give empty text (pure Rust) and need OCR; encrypted PDFs fail or give garbage; huge PDFs need a page cap.
3. Safety. Already have: plugin helpers run as separate processes in a Windows Job Object (memory cap, kill on close, active-process limit; core/src/plugins/wire.rs); tests cover a helper that crashes, hangs or hits the cap costing one call. Content service already caps text at 1 MB (MAX_TEXT_BYTES) and skips by FileClass.
   - To add: max file 50 MB; zip bomb guard (sum of declared uncompressed sizes 100 MB, per-part 20 MB, stream with a hard read limit rather than trusting headers, max 5,000 entries); max 500 PDF pages; 10 s per file; no nested archives.
   - Run extraction in a new helper plugin, not in the daemon.
4. Privacy. Skip: encrypted OOXML (an OLE container, not a zip, so the zip open fails), PDF with /Encrypt. Masking hook is `secrets::mask(&text)` in core/src/content/service.rs (about line 624), applied to all text before indexing. New extractors must return text to that same path; nothing may be stored earlier. Today .pdf classifies as FileClass::Skip (extract.rs test).
5. Index cost (20 generated files: 8 docx, 6 xlsx, 6 pptx; 275 KB on disk, 489 KB extracted text; Python stand-in extraction 123 ms total). So about 24 KB text per document, about 23 MB text per 1,000 documents. The tantivy index size was NOT measured. A rough assumption is 0.5 to 1x the text, so 12 to 25 MB per 1,000 docs. Synthetic text is more repetitive than real files.
6. Recommendation: B, in two steps (A first).
   - A (Office only): effort about 2 days; risk low (zip + quick-xml, bounded, helper isolated).
   - B (A + pure-Rust PDF): effort about 4 to 5 days; risk medium (parser panics, odd encodings; contained by helper and time limit).
   - C (B + OCR scanned PDFs): effort about 8 to 10 days; risk high (CPU and battery, slow indexing, need page render path); do only if users ask.

## Office text search (Option A built): docx, xlsx, pptx

- **Daemon reads the file and sends the bytes** (base64 over the plugin pipe; 50 MB becomes about 67 MB of JSON, within the helper's 1 GiB cap). The helper needs no file permission and opens nothing; the cost is a transient copy of the file in both processes.
- **Dependencies:** zip 9.8.1 (MIT) with only `deflate-flate2-zlib-rs`, quick-xml 0.42.0 (MIT); pure Rust. The zip feature pulls zlib-rs (Zlib licence) through flate2, because flate2 refuses to build with no backend.
- **Limits:** 50 MB per file, 100 MB uncompressed in total (declared and counted while reading), 20 MB per part, 5,000 entries, 10 s, 1 MiB of text. Skips are logged with a reason and recorded empty so they are not retried each scan.
- Office files take the normal idle path only; the helper is opt-in (turned on and approved in the Plugins panel).

## PDF text search (Option B built)

- **Crate: lopdf 0.47.0** (MIT), `default-features = false` (no rayon, no chrono). Checked with `cargo info` and `cargo metadata`: no C code, no build script, no `links`. Chosen over pdf-extract 0.12.1 (MIT, built on lopdf) for finer control: page count, encryption check and a per-page deadline. Transitive licences include BSD-3-Clause (brotli-decompressor, alloc-stdlib), which is outside the rule that applied to the one crate approved.
- **Same helper** (`com.lookout.office-text`, same `extract_office` call with `ext: "pdf"`); the daemon reads the file (at most 50 MB) and sends the bytes. `.pdf` is now `FileClass::Office`, so it follows the same rules: helper off means files are left alone, and a full content index returns before the file is read.
- **Limits:** 50 MB, 500 pages (more is skipped, not truncated), 10 s checked between pages (the initial parse cannot be interrupted; the daemon's 15 s call timeout and the job object cover it), 1 MiB of text. Text goes through `secrets::mask`.
- **Skipped and recorded empty (not retried):** `/Encrypt` anywhere in the file, unreadable or corrupt, over the limits, and "no text layer" (scans; no OCR).
- **Panics:** the parser runs under `catch_unwind`. The release profile has `panic = "abort"`, so there the panic ends the helper process instead, and the process isolation is the only layer; the daemon then sees the call fail and retries that file on the next scan. Not changed here.
- **Measured (release, generated files):** 50-page text PDF, 157 KB of text: 3 ms per file, about 0.06 ms per page. 20 PDFs of 10 pages (666 KB on disk, 551 KB text): index grew 24 KB to 339 KB, so +315 KB, about 0.57 times the text. Generated text from a small vocabulary and a simple Type1 font; real PDFs with embedded fonts, compression and odd encodings will be slower and may extract less.


## One-click semantic setup

- **Network rule.** Your files, searches and index never leave your PC. Lookout connects to the internet only when you click a download button, and it only receives files. Downloads run only from the button, over HTTPS (WinHTTP, TLS 1.2+), to `huggingface.co`, its `*.hf.co` CDN redirect targets and `files.pythonhosted.org`; each redirect hop is re-checked against that list. GET only, no cookies, no authentication, no custom headers, no user data.
- **Pins** (unchanged, same as `plugins/semantic/src/assets.rs`, a test checks it): `Xenova/bge-small-en-v1.5` `onnx/model_quantized.onnx` (34,014,426 bytes), its `tokenizer.json` (711,396 bytes), and `onnxruntime.dll` 1.32.0 from the PyPI wheel `onnxruntime-1.32.0-cp312-cp312-win_amd64.whl` (16,698,767 bytes, wheel SHA-256 pinned too; the dll, 22,668,640 bytes, is the only member extracted and has its own pin). Total download 51,424,589 bytes.
- **Dependencies.** No new crate: `zip` 9.8.1 (already used by the office helper) moves into core; `windows-sys` gets the `Win32_Networking_WinHttp` feature. The plugin executables link `lookout-core`, so this code is in their binaries but is never called.
- **Offline vs unreachable.** Told apart only by WinHTTP's error code (name not resolved or "disconnected" is shown as offline); a captive portal or a blocked DNS can look like either.
- **Not done:** auto-updates, other models, a first-run wizard.

## Shell thumbnails in the file preview

- **Third-party code.** Pictures of Office, PDF, video, audio, archive and other files come from `IShellItemImageFactory`. Whatever thumbnail and icon handlers are installed for a type run for them; this is other vendors' code, and it may run inside Lookout's process. A handler that crashes there can take Lookout down: nothing here prevents that.
- **Never asked:** sensitive-file names, anything the indexer skips (excluded names and folders, `AppData` unless a folder in it was added, Lookout's own data), symbolic links, online-only placeholders, files over 200 MB, and `.lnk` / `.url` / `.pif` shortcuts. The same rules hide the text, image and zip previews, on the disk pages too.
- **Limits:** one new STA thread per request, waited for 2 s. A running handler cannot be stopped; on timeout or a new selection its answer is dropped, and at 3 workers still running no more are started (previews fall back until one returns). The icon is fetched first, so it is what remains when the thumbnail is slow or missing. No error dialog or message.
- **Memory only:** up to 8 thumbnails and 12 MB, dropped 30 s after the bar is hidden. Lookout writes none to disk; Windows keeps its own thumbnail cache. Sent to the window as 32-bit BMP (no new crate or Windows feature), at most 512 px in the panel and 1024 px in the large preview.
- **Zip:** the first 50 names and sizes from the archive's directory, with the existing `zip` crate; nothing is unpacked, names are masked like other text.

## Search operators

- `ext:`, `size:`, `in:`, `name:` are parsed in `core/src/operators.rs` before the other words. Anything that does not read stays a word; a query without operators takes the same path as before.
- **Sizes** are in the name index now (4 bytes a file: whole KiB plus a "bytes remain" bit, so kb/mb/gb comparisons are exact; units are 1024-based). Snapshot format `NIX2`; an older `NIX1` snapshot loads with sizes unknown until the startup crawl. A changed file's size is refreshed from its watcher event.
- **`in:`** matches a folder name by its beginning (`in:down`), parts of a path with whole names before the last (`in:work/rep`), or a full path; only inside the indexed folders.
- Apps are left out while an operator is typed. Content and meaning matches are filtered by path afterwards (a size check reads that file's metadata).
- The extensions offered for `ext:` are counted when a crawl ends, never while typing.
